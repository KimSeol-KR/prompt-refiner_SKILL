# 프롬프트 보정 (의도 복원)

## 이 스킬이 푸는 문제

프롬프트를 잘 못 쓰는 사람의 요청은 **정보가 없는 게 아니라, 머릿속에 있는 상황을 안 적은 것**이다.
"보고서 좀 정리해줘"라고 쓴 사람의 머릿속에는 이미 받는 사람, 마감, 분량, 강조하고 싶은 부분이 다 들어 있다.
그래서 이 스킬의 목표는 "더 좋은 프롬프트를 쓰게 가르치는 것"이 아니라 **빠진 맥락을 최소한의 마찰로 끌어내고, 나머지는 합리적으로 채운 뒤 눈으로 확인시켜 주는 것**이다.

가장 흔한 실패는 두 가지고, 둘 다 피해야 한다.

- **넘겨짚기**: 확인 없이 실행 → 사용자가 원하지 않은 결과물을 받고 "이게 아닌데"로 시작하는 재작업
- **질문 폭탄**: "독자는? 분량은? 톤은? 형식은?" → 비전공자는 이 질문들에 답할 언어가 없어서 지치거나 "알아서 해주세요"로 돌아감

핵심 원칙: **답이 실제로 달라지는 것만 묻고, 나머지는 기본값으로 채운 뒤 보이게 적는다.**

## 이 스킬이 하지 않는 일

대상은 **사용자가 쓴 요청문 하나**이고, 하는 일은 **거기 안 적힌 의도를 복원하는 것**이다. 그 바깥은 다른 일이다.

- **산출물을 더 좋게 만드는 것이 아니다.** 좋은 글쓰기·좋은 코딩 규범은 여기 들어오지 않는다. 기본값조차 "이게 좋다"가 아니라 "사용자가 말했다면 이랬을 것"으로만 정당화된다.
- **안전장치가 아니다.** 되돌릴 수 없는 작업이라도 **의도가 선명하면 묻지 않는다.** 되돌리기 비용은 결손의 무게를 재는 저울이지, 그 자체가 확인 사유가 아니다.
- **에이전트 자기 규율이 아니다.** 사용자 입력이 없는 자리 — 스스로 다음 할 일을 정하는 순간 — 에는 보정할 대상이 없다.
- **프롬프트 쓰는 법을 가르치는 것이 아니다.** 사용자는 다음에도 똑같이 대충 쓸 것이고, 그래도 되게 만드는 게 목표다.

새 규칙을 넣고 싶을 때 **"이게 사용자가 쓴 문장에서 의도를 복원하는 일인가"**를 먼저 묻는다. 아니면 넣지 않는다.

## 언제 쓰고 언제 쓰지 않는가

먼저 원문을 읽고 판단한다. 판단 자체는 티 내지 말고 조용히 한다.

**보정하고 확인받는다** — 아래 중 하나라도 해당할 때
- 결손이 2개 이상이거나, 결손 하나가 결과물 전체를 좌우한다 (`references/gap-types.md`)
- 결손이 하나뿐이어도 **틀렸을 때 되돌릴 수 없다**: 파일 덮어쓰기·삭제, 발송, 외부 게시, 대량 변경
- 작업이 길다: 만들다가 방향이 틀렸다는 걸 알면 손해가 큰 경우

가운데 항목은 **되돌릴 수 없으면 무조건 묻는다는 뜻이 아니다.** 이 스킬은 안전장치가 아니라 의도 복원 장치다.
판단 순서는 언제나 같다 — **먼저 결손이 있는지 보고, 결손이 있을 때 그 무게를 되돌리기 비용으로 잰다.**
"`temp.log` 지워줘"처럼 의도가 이미 선명하면 결손이 없으므로 그냥 실행한다. 반면 "정리 좀 해줘"는 결손 하나(무엇을 어디까지)만으로도 파일이 사라질 수 있으니 확인한다.
같은 삭제 요청이라도 앞의 것은 안 묻고 뒤의 것은 묻는 이유가 여기 있다.

**보정하지 않고 바로 실행한다**
- 단순 사실 질문, 한 줄 답이면 끝나는 것
- 요청이 이미 구체적일 때 (형식·범위·목적이 이미 적혀 있음)
- 결과물이 가볍고 바로 다시 시키면 되는 경우 → 대신 **실행하고 나서** 한 줄로 "이 기준으로 했는데, 다르면 말해줘"를 붙인다
- 사용자가 명시적으로 "묻지 말고 그냥 해"라고 했을 때 → 가정만 한 줄로 적고 실행

애매하면 실행 쪽으로 기운다. 확인 카드를 남발하면 사용자는 스킬이 켜져 있다는 사실 자체를 귀찮아하게 된다.

## 절차

### 0단계 — 질문을 만들기 전에, 찾을 수 있는 건 먼저 찾는다

**이 순서를 지키는 게 중요하다.** 물어보기로 마음먹고 나면 "확인 차" 묻게 되는데, 사용자 입장에서는 찾아보지도 않고 물은 것과 구별되지 않는다. 질문 목록을 만들기 **전에** 손이 닿는 곳을 훑는다.

- 연결된 폴더·첨부파일·이전 대화에 재료가 있는지
- 파일 목록에서 후보를 특정할 수 있는지
- 프로젝트 문서(CLAUDE.md 등)에 이미 답이 있는지
- **연결된 도구에 이미 있는지** — Notion·Drive·Slack 같은 커넥터, 저장된 메모리. 로컬 파일만 훑고 "재료가 없다"고 판정하는 것이 이 스킬의 가장 비싼 실패다. 사용자의 기획서는 대개 파일이 아니라 문서 도구에 있다.

**특히 "기존 문서가 있을 법한 일"에서 이 단계를 건너뛰면 치명적이다.** 기획·설계·정책처럼 사용자가 이미 써둔 것이 있을 가능성이 높은 주제에서, 찾아보지 않고 새로 만들면 그럴듯하지만 전제가 다른 산출물이 나온다. 사용자는 그게 틀렸다는 걸 한참 뒤에 발견한다. **없는 것을 만드는 것보다, 있는 것과 어긋나는 것을 만드는 쪽이 훨씬 해롭다.**

찾았으면 묻지 말고 확인만 받는다 — "Downloads의 `매출_최종.xlsx` 말씀이시죠?"
못 찾았으면 그때 질문에 넣되, **못 찾은 이유를 한 줄로 밝힌다**. "폴더 연결이 안 돼 있어서 파일을 못 봅니다" 한 줄이 있고 없고가 체감을 가른다.

### 1단계 — 원문을 세 칸으로 쪼갠다

머릿속에서 (출력하지 말 것):

- **확정**: 사용자가 실제로 쓴 말. 고유명사, 숫자, 지정한 파일, 사용자가 쓴 용어 — 이건 절대 바꾸지 않는다.
- **추론**: 정황상 거의 확실한 것. "회의록 정리"라면 시간순 정리, 결정사항 강조 정도.
- **공백**: 없는데 결과를 바꾸는 것. 여기서만 질문이 나온다.

### 2단계 — 진짜 목적을 먼저 찾는다

공백 중 하나만 물을 수 있다면 **"이걸로 뭘 하려는지"**를 묻는다. 목적을 알면 형식·분량·톤은 대부분 따라 나오기 때문이다.

- "보고서 정리" + "내일 팀장님 보고" → 분량·톤·강조점이 한 번에 정해진다
- "코드 고쳐줘" + "내일 시연" → 리팩터링이 아니라 최소 수정이 정답이 된다

원문에 목적이 이미 드러나 있으면 다시 묻지 않는다. 이미 답한 걸 또 묻는 것이 사용자가 가장 싫어하는 일이다.

### 3단계 — 공백을 기본값으로 메운다

남은 공백은 `references/defaults.md`의 작업 유형별 기본값으로 채운다. 채운 것은 반드시 확인 카드에 보이게 적는다. 조용히 가정하고 넘어가면 넘겨짚기와 같아진다.

### 4단계 — 최대 2개만 묻는다, 선택지로

기본값으로 못 메우는 것만 남긴다. 그중 **결과물이 눈에 띄게 달라지는 것 위주로 최대 2개**.

질문은 열린 질문이 아니라 **선택지 + 각 선택의 결과**로 낸다. "형식은 어떻게 할까요?"에는 답을 못 해도, "표로 vs 줄글로"에는 누구나 답한다.

```
분량을 어느 쪽으로 할까요?
  A) 한 장 요약 — 팀장님이 회의 직전 훑어보기 좋음
  B) 3~4장 상세 — 근거까지 다 들어가지만 읽는 데 시간 걸림
```

용어는 사용자의 언어로 쓴다. "톤앤매너", "스코프", "포맷" 대신 "말투", "어디까지", "형태".
선택지를 만들 수 있으면 `AskUserQuestion` 도구를 쓰고, 없으면 위 형식 그대로 글로 낸다.

### 5단계 — 확인 카드를 보여준다

10초 안에 읽히게. 이 형식을 쓴다:

```
이렇게 이해했어요 — 맞으면 진행할게요.

**하려는 것**: (한 문장. 사용자 말이 아니라 실행 가능한 문장으로)
**만들 것**: (산출물 형태와 크기)
**이렇게 가정했어요**: (기본값으로 채운 것 1~3개, 각 한 줄)

확인하고 싶은 것:
1. (질문 + 선택지)
2. (질문 + 선택지)

"그냥 진행"이라고 하시면 위 가정대로 바로 만들게요.
```

가정이 없으면 그 줄은 빼고, 질문이 없으면 질문 절을 뺀다. 빈 칸을 채우려고 억지로 만들지 않는다.
**"그냥 진행" 탈출구는 항상 남긴다.** 질문에 답하기 싫은 사용자가 막히지 않게 하는 장치다.

**재료가 없으면 카드를 뒤로 미룬다.** 대상 파일이나 코드를 못 봤으면 "만들 것"과 "가정"을 쓸 수가 없다. 억지로 쓰면 지어낸 소리가 된다.
이때는 카드 대신 필요한 질문만 던지고, **결과물을 만든 뒤에 가정을 붙인다**.

```
(결과물)

---
**이렇게 가정하고 넣었어요** — 다르면 말씀해주세요.
- (가정 1)
- (가정 2)
```

사후 카드는 실물을 놓고 고치는 거라 사용자가 판단하기 오히려 쉽다. 그래서 아래 두 경우에 쓴다.

- 재료를 못 봐서 가정을 미리 쓸 수 없을 때
- 결과물이 가볍고 되돌리기 쉬워서, 만들어 보여주는 게 말로 정하는 것보다 빠를 때 (짧은 글, 요약, 목록)

**반대로 아래는 반드시 사전 카드다.** 여기서 사후로 미루면 스킬이 있으나 마나 해진다.

- 결손이 남아 있는데 되돌릴 수 없는 작업 (삭제·덮어쓰기·발송·일괄 변경)
- 만드는 데 오래 걸려서 방향이 틀리면 손해가 큰 작업

다시 말하지만 **결손이 없으면 아무것도 묻지 않는다.** 되돌릴 수 없다는 사실만으로 카드를 띄우는 건 이 스킬의 일이 아니다.

판단이 서지 않으면 **"틀렸을 때 버리는 비용"**으로 가른다. 버려도 아깝지 않으면 만들어서 보여주고, 아까우면 먼저 묻는다.

### 6단계 — 승인 후 실행

승인되면 확인한 내용대로 실행한다. 카드에 없던 범위를 임의로 늘리지 않는다.
사용자가 "그냥 진행"을 골랐다면 가정대로 하되, 결과 끝에 한 줄로 어떤 가정을 썼는지 다시 짚어 준다.
사용자가 카드를 고쳐 주면 고친 내용이 원문보다 우선한다.

## 절대 하지 않을 것

- **사용자 어휘 바꾸기**: 사용자가 "냉가노"라고 부르면 "냉장고 파먹기"로 고쳐 쓰지 않는다. 사용자 용어가 곧 사용자 의도다.
- **범위 늘리기**: "제목 좀 고쳐줘"에 본문까지 손대지 않는다. 보정은 의도를 선명하게 하는 것이지 크게 만드는 것이 아니다.
- **답한 것 다시 묻기**: 원문·이전 대화·첨부파일에 있는 정보는 이미 답이다.
- **가르치려 들기**: "이렇게 프롬프트를 쓰시면 더 좋습니다" 같은 훈수는 요청받지 않으면 하지 않는다.
- **3개 이상 묻기**: 정말 못 정하겠으면 기본값으로 정하고 카드에 적는다. 사용자는 만들어진 결과를 보고 고치는 게 더 쉽다.

## 참조 파일

- `references/defaults.md` — 작업 유형별(글쓰기/조사/코딩/정리/제작) 기본값 사전. 3단계에서 채울 값을 고를 때 읽는다.
- `references/examples.md` — 실제 before/after 5건. 카드 톤과 질문 만드는 감을 잡을 때 읽는다.
